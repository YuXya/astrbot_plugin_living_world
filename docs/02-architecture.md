# Living World 总体架构

> **English Summary:** Living World is a modular monolith with twelve modules grouped into six workflows and eleven runtime event families; Contracts defines and validates schemas but does not publish or consume a runtime family. Runtime modules exchange versioned messages through one bus, own their data exclusively, and keep AstrBot conversation history outside the plugin's shared AI-life memory.

## 1. 架构目标

架构需要同时满足：

- 一个插件内完成部署、升级和诊断，降低 1.0 运维复杂度。
- 十二个模块可以按事件契约并行开发、独立测试和安全降级。
- 同一个 AI 的生活在所有会话中连续一致，但用户聊天历史继续按 AstrBot 会话隔离。
- 外部天气、新闻、搜索和 B 站能力不是核心循环的单点故障。
- 主动行为可解释、可停止、可去重且可审计。

采用模块化单体；选择理由与代价见 [ADR-0001](adr/0001-modular-monolith.md)。

## 2. 系统边界

```text
AstrBot 会话历史 ──按目标临时读取──┐
                                  │
和风天气 ─┐                       │
新闻/搜索 ├─> Living World 消息总线 ─> 生活循环 ─> 主动候选 ─> OneBot QQ
B站公开能力┘                       │
                                  └─> 管理页面 / 审计投影
```

- AstrBot 负责插件生命周期、消息接入、会话隔离、原始聊天历史和 LLM 能力。
- Living World 负责 AI 身份、世界、日程、状态、生活记忆、公开信息观察、对象池和主动行为。
- OneBot / `aiocqhttp` 是 1.0 的主动投递适配目标。
- 和风天气、新闻、搜索和 B 站是外部感知源；它们的原始实现不得渗透到领域模块。

## 3. 六条工作流与十二个模块

| 工作流 | 模块 | 唯一职责 |
|---|---|---|
| 基础 | `contracts` | 定义并验证统一消息信封、十一种运行时事件族、命令/查询语义和版本兼容规则；不在运行时消费或发布 `contracts.*` |
| 基础 | `kernel` | 总线、时钟、生命周期、任务监管、存储基础设施和恢复协调 |
| 世界模拟 | `world` | 插件自有的 AI 身份、世界知识和设定 |
| 世界模拟 | `planner` | 基于时间、设定和观察决定 AI 计划做什么 |
| 世界模拟 | `state` | 表达并推进 AI 实际正在做什么以及状态变化 |
| 记忆与上下文 | `memory` | 持久化 AI 自己的生活账本并提供只读检索投影 |
| 记忆与上下文 | `conversation` | 按目标读取 AstrBot 原生会话并组装本次临时上下文 |
| 感知 | `environment` | 获取、缓存并标准化现实天气与位置相关环境事件 |
| 感知 | `exploration` | 通过新闻、AstrBot 搜索和 B 站公开能力形成有来源的观察 |
| 社交与行动 | `audience` | 维护主动对象资格、基础权重、事件相关性排序和免打扰资格 |
| 社交与行动 | `proactive` | 生成主动候选、逐目标个性化、OneBot 投递和结果审计 |
| 运营 | `admin` | 配置、命令、完整管理页、诊断、导入导出和审计投影 |

“唯一职责”既是设计边界也是数据所有权边界。十二个模块中，`contracts` 是定义/验证契约的静态模块，不是运行时事件族；其余十一个模块分别拥有 `kernel`、`world`、`planner`、`state`、`memory`、`conversation`、`environment`、`exploration`、`audience`、`proactive`、`admin` 运行时事件族。模块可以公开事件和请求处理器，不公开内部仓储或可变对象。

## 4. 依赖与通信规则

### 4.1 允许的依赖

- 业务模块可以依赖 `contracts` 中的稳定消息定义。
- `main.py` 可以在装配阶段创建模块、注入总线端口并注册处理器。
- `kernel` 提供基础设施端口和测试替身，但不包含世界、记忆或主动业务规则。
- 平台与外部服务适配器实现相应模块拥有的端口，并把结果转换为公共事件。

### 4.2 禁止的依赖

- 业务模块直接导入另一个业务模块的实现。
- 调用另一个模块的仓储、服务、内部函数或可变状态。
- 读取、联表或修改另一个模块拥有的数据表。
- 通过全局单例、回调闭包或 AstrBot 消息对象绕过总线传业务数据。
- 管理页面直接修改任何业务存储。

所有跨模块动作都经过版本化消息总线。需要返回值的读取也发送请求消息，并通过同一总线接收带匹配 `correlation_id` 的响应；不得以“只是查询”为由直连。

管理路由同样遵循领域所有权：`admin` 受理 UI/命令并完成鉴权与关联后，以目标领域事件族发布 `Command`（例如 `world.*`）；目标领域以自己的事件族发布事实、响应或失败。`admin.*` 仅表示管理操作生命周期、审计关联和只读投影更新，其他领域不得把它当作直接业务命令消费。

### 4.3 组合根

`main.py` 只负责：

1. 接收 AstrBot 上下文和生命周期信号。
2. 创建配置、时钟、总线及模块实例。
3. 注册消息处理器和公开命令。
4. 在卸载时按顺序停止模块并释放资源。

领域决策、提示词拼装、天气处理或主动选择逻辑不得放在 `main.py`。

## 5. 数据所有权

| 数据 | 唯一写入所有者 | 其他模块的访问方式 |
|---|---|---|
| 消息契约与版本定义 | `contracts`（定义，不持久化） | 代码依赖和契约测试 |
| 总线运行状态、任务与恢复元数据 | `kernel` | 内核事件或诊断请求 |
| AI 身份、世界设定与叙事地点目录 | `world` | 世界快照事件或查询响应；不拥有现实天气查询位置配置 |
| 日程与计划 | `planner` | 计划事件或查询响应 |
| 当前/历史状态转换与当前叙事位置状态 | `state` | 状态变化事件或查询响应；不拥有现实天气查询位置配置 |
| AI 生活账本 | `memory` | 生活记忆查询响应 |
| AstrBot 会话历史 | AstrBot，不属于本插件 | `conversation` 按目标即时读取；不得持久化副本 |
| 现实天气查询位置配置（经纬度、城市 ID、时区关联）、天气缓存与环境快照 | `environment` | 环境事件或查询响应 |
| 外部观察及来源元数据 | `exploration` | 观察事件或查询响应 |
| Opaque target reference、对象资格、权重、免打扰与退出状态 | `audience` | 受限 `operational` 目标选择响应和资格事件 |
| 主动候选、路由结果、投递结果与脱敏审计 | `proactive` | 受限 `operational` 主动事件或审计查询响应 |
| 管理视图与诊断投影 | `admin` | 管理 API；不成为业务事实来源 |

具体数据库、表和迁移方案不在总体架构中锁定；确定后必须保持上述单写者原则。

## 6. 核心事件流

```text
environment / exploration 发布有来源的观察
                    ↓
planner 根据时间、世界设定和观察更新计划
                    ↓
state 推进实际生活状态并发布生活事件
                    ↓
memory 记录 AI 自己的生活账本
                    ↓
proactive 形成可发送候选
                    ↓
audience 计算资格与排序，返回前 N 个目标
                    ↓
conversation 分别读取每个目标的 AstrBot 会话上下文
                    ↓
proactive 分别个性化生成，经 OneBot 投递并记录受限运营结果
                    ↓
proactive 发布自身 family 的 `proactive.life_action_completed` ai_life 新根 Event，memory 订阅并通过隐私准入后记账；admin 更新只读审计投影
```

关键约束：

- 一次事件可以产生零个、一个或多个主动候选；生活事件不等于必须发消息。
- 每个目标独立组装上下文和生成，不能把 A 会话内容带入 B 会话。
- Opaque target reference、免打扰/退出/权重、路由结果和脱敏投递审计属于受限 `operational` 数据，仅供 `audience`、`proactive`、`admin` 最小使用，并受访问、导出和删除控制；不得进入生活记忆或跨目标内容。
- 主动行为完成后的生活回写必须是隐私断开的最小 `ai_life` 新根事件：只含动作类型、结果、时间和源生活事件，不含目标/会话 ID、文本或可反查标识，也不沿用 `session_scoped` 链路的 correlation/causation/trace。
- 每个主动候选最多回写一条目标无关的聚合生活事实；首次创建的稳定幂等身份与 message/correlation/trace 在重放时复用，不得由目标、会话或逐目标键推导，也不得与受限投递审计形成可反查映射。生活事实不含目标数量、逐目标结果或逐目标键；具体字段与算法另立 ADR。
- 失败与重试策略后续配置化；任何重试都必须复用幂等身份，避免重复投递。

## 7. 身份与上下文分层

生成上下文按以下逻辑分层，具体提示词格式由后续 ADR 决定：

1. 插件自有 AI 身份与世界规则。
2. 当前时间、日程、状态、天气和相关生活记忆。
3. 本次公开信息观察及来源。
4. 仅属于当前目标的 AstrBot 原生会话上下文。
5. 当前任务与输出约束。

用户应为相关会话选择空白 AstrBot 人格，以避免身份重复或冲突。Living World 的动态上下文仅参与本次生成，不写回 AstrBot 历史；正常机器人回复是否进入历史仍由 AstrBot 自身机制决定。

## 8. 运行与降级

- 外部感知模块失败：发布能力不可用或数据陈旧状态，生活循环使用最后有效且带时间标记的信息，或在无信息模式继续。
- LLM 生成失败：不投递半成品；记录不含敏感正文的失败审计。
- OneBot 不可用：候选进入失败/待处理状态，具体重试次数后续决定；不得无限发送。
- 单个处理器失败：由 `kernel` 隔离并报告，不应阻塞无关事件消费者。
- 重启恢复：各模块从自己的持久化状态和幂等记录恢复；不能靠扫描 AstrBot 聊天历史重建 AI 生活。
- 管理模块失败：核心生活循环可继续；管理员仍应能通过最小诊断命令发现状态。

## 9. 架构守卫

P8 应建立自动检查，至少覆盖：

- 业务模块之间不存在直接实现导入。
- 只有数据所有者写入对应存储。
- 所有消息符合信封和版本规则。
- 重复、乱序消息不会重复产生关键副作用。
- 会话 A 的内容不会出现在会话 B 的上下文、记忆或审计中。
- 主动投递必须经过对象资格、免打扰和去重检查。
- 外部适配器不可用时，核心模块可用模拟事件运行。
