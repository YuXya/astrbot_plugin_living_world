# Living World 主程计划

> **English Summary:** The lead owns architecture, public contracts, integration, and release. Nine clearly bounded workstations build in dependency-ordered waves, with contract-first development, module ownership, and explicit quality gates.

## 1. 主程职责与决策权

P0 主程对以下事项拥有最终合并责任：

- 产品边界与 1.0 验收口径。
- 公共事件语义、版本策略和跨模块兼容性。
- ADR 的接受、废弃与替代。
- 根目录文件、AstrBot 主入口、模块装配和发布版本。
- 跨模块冲突、风险取舍、发布阻断与最终签署。

主程不替模块负责人决定尚未评审的内部实现细节。数据库表、天气字段、状态数值、新闻源、重试次数、记忆检索算法和 LLM 预算由对应负责人提出方案，经专题评审和 ADR 锁定。

## 2. 九个工位

| 工位 | 角色 | 唯一负责范围 | 主要交接对象 |
|---|---|---|---|
| P0 | 主程 / 架构 / 集成 | `contracts` 语义、ADR、根文件、主入口、契约冻结、评审、合并、最终发布 | 全员 |
| P1 | 内核工程师 | `kernel`、消息总线、时钟、生命周期、任务监管、持久化基础设施、恢复 | P0、P2、P8 |
| P2 | 世界模拟工程师 | `world`、`planner`、`state`，身份世界、日程和实际生活状态 | P1、P3、P4 |
| P3 | 记忆上下文工程师 | `memory`、`conversation`，AI 生活账本和 AstrBot 原生上下文接入 | P2、P6、P8 |
| P4 | 环境工程师 | `environment`，和风天气、位置、缓存和标准化环境事件 | P2、P5、P8 |
| P5 | 探索集成工程师 | `exploration`，新闻、AstrBot 搜索和 B 站公开能力适配 | P2、P6、P8 |
| P6 | 社交主动工程师 | `audience`、`proactive`、OneBot 投递、对象池和主动链路 | P3、P5、P7 |
| P7 | 管理前端工程师 | `admin` 与 Plugin Page，配置、查看、编辑、诊断和审计 | 全模块负责人、P8 |

每个工位的执行说明以 `work-packages/` 中对应任务卡为准。模块负责人只修改自己的模块、测试和任务卡；共享契约与根文件由 P0 串行合并。

## 3. 工作方式

### 3.1 契约优先

1. 负责人先用事件示例表达所需输入、输出和失败语义。
2. 在修改公共契约或实现前，P0 与生产方、消费方共同评审：补充现有契约 ADR 的变更记录；若改变已接受结论，则新增或替代 ADR，并先取得接受状态。
3. 按已接受 ADR 先新增或修改契约测试，覆盖旧兼容行为和拟议新行为。
4. 再更新事件契约与实现；契约冻结后，各模块使用模拟事件独立开发。
5. 只有契约测试通过后才进入真实总线联调。

不得先通过直接导入或共享数据库“临时打通”，再补事件契约。

### 3.2 目录与数据所有权

- `contracts` 是唯一公共语义依赖，不拥有业务数据，也不是运行时事件族；它只定义并验证其他十一个运行时事件族的契约。
- 每个业务模块拥有自己的写入模型；其他模块只能通过总线获取事件或请求只读投影。
- `main.py` 是装配根，仅做 AstrBot 适配、依赖创建和模块注册。
- `admin` 不直接修改任何业务模块的表或内存状态。它受理管理操作后，以目标领域事件族发布 `Command`；`admin.*` 只用于管理操作生命周期、审计关联和只读投影，不作为领域业务命令。
- AstrBot 是原始消息和会话历史的唯一所有者；本插件不得建立副本。

### 3.3 评审与合并

每个变更至少满足：

- 关联任务卡和验收标准。
- 仅触及负责人允许范围；越界变更须由对应所有者共同评审。
- 任何公共契约变更都必须有先行的已接受 ADR 记录和先行契约测试，再同步更新示例、版本说明与实现。
- 包含正常、重复、乱序、无外部能力和重启后的相关测试。
- 不含跨会话消息正文、第三方私有接口或许可证不明内容。

P0 负责按依赖顺序串行合并公共契约；P8 可因隐私泄漏、许可证风险、数据破坏或防重复发送失败阻断发布。

## 4. 四个并发工位的波次

### 波次 0：基础冻结

- P0：冻结产品边界、公共术语、第一版事件信封和 ADR。
- P1：实现内核最小能力及测试替身。
- P8：建立契约测试、架构守卫和发布检查框架。
- 空余工位：由 P0 轮值进行 AstrBot/OneBot 骨架验证，不提前写业务模块。

退出条件：模块能仅依赖公共契约和模拟总线启动测试；基础契约有明确版本。

### 波次 1：生活与感知

- P2：`world`、`planner`、`state`。
- P3：`memory`、`conversation`。
- P4：`environment`。
- P5：`exploration`。

退出条件：不用真实主动发送即可形成“观察 → 日程/状态 → AI 生活事件 → 共享生活账本”闭环。

### 波次 2：社交、运营与集成

- P6：`audience`、`proactive` 和 OneBot 适配。
- P7：`admin` 与 Plugin Page。
- P0：集成、契约升级和跨模块问题裁决。
- P8：隐私、故障、去重与黑盒测试。

退出条件：前 N 目标选择、逐会话个性化、免打扰、审计和管理能力端到端通过。

### 波次 3：稳定与发布

- 固定工位：P0、P1、P8。
- 第四工位：按当前最高风险选择一名模块负责人轮值。

退出条件：迁移、恢复、OneBot 实测、全新克隆验证、文档和公开发布检查全部通过。

## 5. 质量门禁

| 门禁 | 必须证明的结果 |
|---|---|
| 骨架门禁 | 插件可加载、热重载、卸载，健康命令可用；无数据库、后台任务和真实主动消息 |
| 基础门禁 | 事件信封、总线、时钟和测试替身稳定；业务模块之间无直接实现导入 |
| 生活门禁 | 世界、计划、实际状态、天气和生活账本形成可恢复闭环 |
| 感知门禁 | 新闻、搜索、B 站观察均有来源，能力缺失时可降级 |
| 主动门禁 | 对象池、个性化、免打扰、去重、审计和 OneBot 投递通过 |
| 管理门禁 | Plugin Page 把操作路由为目标领域事件族的 `Command`；`admin.*` 仅承载管理生命周期、审计关联和只读投影，不绕过数据所有权 |
| 发布门禁 | 隐私、许可证、迁移、故障、文档与远端全新克隆验证全部通过 |

## 6. 主要风险与负责人

| 风险 | 防线 | 负责人 |
|---|---|---|
| 跨会话泄漏用户对话 | 数据分类、架构守卫、隐私测试，禁止复制聊天正文 | P3、P8 |
| 主动消息重复或失控 | 幂等键、免打扰、频率约束、投递审计和总开关 | P6、P8 |
| 模块形成隐式耦合 | 仅依赖契约、跨模块总线、禁止共享表 | P0、P1、P8 |
| 外部源不可用或污染 | 来源标识、超时/降级、陈旧标记、模拟故障测试 | P4、P5 |
| 参考项目许可证污染 | 来源登记、clean-room 评审和贡献声明 | P0、P8 |
| 人格与 AstrBot 人格叠加 | 部署文档要求使用空白 AstrBot 人格，运行诊断给出提示 | P0、P7 |

## 7. 变更控制

任何公共契约变更都必须先更新现有契约 ADR 的变更记录，或新增/替代 ADR，并先补契约测试；不能只在实现、文档正文或 PR 描述中决定。以下变更改变已接受的基础结论，必须新增或替代 ADR，不能只补充旧 ADR：

- 跨模块通信不再全部经过消息总线。
- 改变 AI 生活与用户会话的共享边界。
- 支持非空 AstrBot 人格叠加或多人格生活。
- 扩大首发平台范围或改变 OneBot 优先级。
- 引入会影响 MIT 发布的依赖、代码或资源。
- 引入 AI 与其他 LLM 的自主持续聊天。

发生紧急故障时可以先关闭外部能力或主动投递，但不能绕过隐私边界或数据所有权。
